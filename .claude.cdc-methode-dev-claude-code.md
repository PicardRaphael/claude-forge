## 3. Pipeline de feature (Q2)

Le pipeline proposé (ticket → architect → TDD → dev → review → perf/sécu) **est l'état de l'art, à une correction de pilotage près** : il est orchestré par la **session principale via skill, JAMAIS piloté par hook** [Anthropic + Forge].

[Web/Anthropic confirmé] : *"Skills are model-invoked — Claude decides when to load them based on your prompt and the skill's description"* ; *"Claude decides whether to delegate."* La session décide quand appeler l'architecte — pas un `architect-guard`.

Pipeline feature M/L :
```
1. Spec (skill /spec ou BRIEF auto-suffisant) → interview AskUserQuestion EN SESSION PRINCIPALE
2. architect-deep si archi non triviale (sinon skip — risque accepté ~20%)
3. Boucle TDD : test-writer → dev → reviewer  (sub-agents scopés)
4. /go : typecheck + tests ciblés + review+autofix (cap 2 itérations) + changelog — STOP avant commit
5. checkpoint humain / CI verte → /ship (commit + push + PR)
```

Fix rapide : description directe → dev → /go. Pas d'architect si trivial.

**Pattern ESCALADE (corrige l'exigence "agent demande toujours")** : un sub-agent qui détecte une ambiguïté n'invente pas et ne peut pas demander. Il STOP et retourne un bloc structuré (Contexte / Ambiguïté / Options+tradeoffs / Recommandation / Question / État fichiers) à la session principale, qui appelle `AskUserQuestion` puis le re-dispatche. Hook `escalade-detector` (SubagentStop) surface le marker, non-bloquant.

**Orchestration massive** : pour les fan-outs déterministes (migrer N modules, auditer N fichiers), Dynamic Workflows natif [Web] — Claude écrit son script d'orchestration, contexte hors-bande, seul l'output final revient. PAS un agent orchestrateur custom (anti-pattern forge).

## 3bis. Context management pour agents — le facteur clé de qualité (Q3)

Le commanditaire le nomme "facteur clé de qualité" — à juste titre. Un contexte pollué dégrade chaque décision de l'agent. À graver dans le CDC [Forge/Anthropic, workflow-claude-code-optimal] :

- **/clear entre tâches non liées** — session fourre-tout = piège #1 de Boris. Pollution du contexte = qualité aléatoire.
- **/compact "garder le plan" proactif à ~70%** de contexte — compresse en préservant le plan en cours.
- **Document-and-clear** — dumper le plan dans un `.md`, /clear, la session fraîche relit le `.md`. Évite la dérive sur les chantiers longs.
- **Sub-agents pour la recherche** — déléguer l'exploration bruyante (lire 40 fichiers) à un sub-agent qui renvoie un RÉSUMÉ, pas le détail. Garde le contexte principal propre. C'est l'une des deux seules raisons valides de créer un sub-agent (l'autre = parallélisme).
- **Running implementation notes** [Thariq] — `docs/implementation-notes/<slug>.md` pré-rempli (objectif, décisions, état, prochaines étapes). Survit aux /clear et /compact, sert de mémoire de travail durable de la feature. Skill `/notes` côté forge.
- **Dynamic Workflows** pour le fan-out massif — orchestration hors-bande, seul l'output final revient au contexte (cf §3).

Ces pratiques ne sont PAS optionnelles sur un repo développé 100% par agents : sans elles, les sessions longues dérivent silencieusement.

## 4. TDD avec l'IA — pourquoi test-first, comment l'outiller sans hook (Q4)

**Pourquoi non négociable** [Web] : CodeRabbit (470 PRs) → IA = 1,7× défauts, logique +75%, perf ×8 ; Uplevel (800 devs) → +41% bugs avec Copilot. Le test écrit AVANT le code IA est le seul filet qui transforme une intention vérifiable en garde-fou.

**Comment l'outiller SANS hook bloquant** :
- Test-first par **convention d'agent** (`test-writer` avant `dev`) + skill, pas par hook PreToolUse — un hook qui exige un fichier test produit des tests cosmétiques qui passent à vide.
- La VRAIE garde = **mutation testing** : la couverture ment (100% couverture ≠ tests qui vérifient). [Web] Stryker (TS/JS) en CI **planifiée** (hebdo, pas chaque PR — coûteux), seuil de **score de mutation > 80%** sur la couche application/use-cases. Un test cosmétique laisse survivre les mutants → la CI le révèle. C'est ainsi qu'on attrape les tests IA "verts mais vides".
- Tests **adverses** sur le code critique (ratio ≥ 3:1 sur les gardes sécu), pas seulement le happy path.

## 5. "Give Claude a way to verify its output" (Q5) — la CI est le capteur PRIMAIRE

Conséquence directe du "100% par agents, par PR" : aucun humain ne lance rien en local, donc **la CI EST le mécanisme de vérification**, pas un complément.

Doit tourner sur CHAQUE PR (Turborepo `--affected` pour ne rebuilder/tester que le graphe impacté) :
- `tsc --noEmit` (types stricts) · `vitest` (tests) · `eslint` · `build`
- **Parité de migration Drizzle** sur une base éphémère (la migration s'applique proprement sur un tenant neuf)
- **Contrat OpenAPI** : la spec générée depuis Drizzle+Zod `.openapi()` ne diverge pas de la spec committée [Web] — protège NeoIA (consommateur Python) d'un breaking change silencieux
- (planifié) mutation testing Stryker, seuil 80%

En local, `/go` rejoue typecheck + tests ciblés + review avant de proposer le push : l'agent voit le rouge AVANT la CI. La CI reste le gate dur, `/go` le pré-vol.

## 6. Ce qui rend le repo AI-agent-friendly — à IMPOSER dans le CDC (Q6)

- **Frontières mécaniques** : hexagonal vérifié par hook (`guard-core-imports`) + ESLint boundaries — domain n'importe jamais db. L'erreur est rendue IMPOSSIBLE, pas déconseillée.
- **Source de vérité unique** : Drizzle = schéma DB ET, via `.openapi()`, contrat OpenAPI [Web]. Un seul endroit à changer → zéro dérive contrat/DB/types/client.
- **Nommage prévisible + colocation** : `[verbe]-[entite].use-case.ts`, `[entite].repository.pg.ts`, test colocalisé `__tests__/`. L'agent déduit l'emplacement sans chercher → moins d'hypothèses fausses (cause #1 des bugs IA).
- **Types stricts** : `tsc` strict, Zod v4 en frontière runtime. Le compilateur attrape la classe d'erreurs que l'IA produit le plus.
- **Zéro ambiguïté** : packages `@neoteem/*` à responsabilité unique, frontières d'import explicites, conventions par chemin dans `.claude/rules/`.
- **Verifiable checkpoints** [Anthropic/Erik Schluntz] : chaque étape mécaniquement vérifiable (type, test, lint, migration, contrat). C'est ce qui permet aux agents de tourner en autonomie sans dégrader.

## Section CDC concrète à insérer

Titre : **"Méthode de développement assisté par agents (Claude Code)"**, 6 sous-sections :
1. **Structure `.claude/`** — CLAUDE.md orchestrateur < 200L + imbriqués par package ; catalogue skills/agents/hooks ci-dessus.
2. **Pipeline de feature** — spec → architect (conditionnel) → TDD (test-writer→dev→reviewer) → /go → CI → /ship. Orchestré par skill, jamais par hook. Pattern ESCALADE obligatoire.
3. **Context management** — /clear, /compact, document-and-clear, sub-agents-pour-recherche, running implementation notes. Le facteur clé de qualité.
4. **Vérification (CI = capteur primaire)** — pipeline CI sur chaque PR (types/tests/lint/build/migration-parité/contrat-OpenAPI), Turborepo affected, mutation testing planifié.
5. **TDD outillé sans hook bloquant** — test-first par convention d'agent + Stryker > 80% en CI planifiée + tests adverses.
6. **Repo AI-friendly par construction** — frontières mécaniques, source de vérité unique (Drizzle→OpenAPI), nommage prévisible, types stricts, colocation.
