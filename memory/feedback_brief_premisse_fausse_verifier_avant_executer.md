Un brief de mission (même détaillé, même avec méthode A→E) n'est pas une source de vérité : il encode l'intention de Raphael à un instant T, pas l'état réel du repo. Avant d'exécuter une instruction qui repose sur une prémisse factuelle (« le fichier X contient N lignes ad-hoc », « la garde Y existe », « le déploiement Z reste à faire »), la vérifier matériellement. Si la prémisse est fausse, surfacer l'écart + ré-arbitrer le périmètre via AskUserQuestion — ne jamais exécuter le brief littéralement sur une base fausse.

**Why:** 27 mai 2026 — brief « nettoyer settings.json claude-forge, ~66 lignes de permissions ad-hoc accumulées ». Vérif empirique : `settings.json` versionné = 163L mais DISCIPLINÉ (chaque entrée a un commit traçable, 11 hooks tous vivants, 23L de permissions seulement). La vraie dette ad-hoc (38/51 entrées mortes/redondantes : cp/sed/node -e morts, git -C doublon de git *, MCP) était dans `settings.local.json` (gitignored, perso) — un fichier que le brief ne mentionnait même pas. Exécuter le brief littéralement = épurer le mauvais fichier pour un gain marginal et rater 95% de la dette. Surfacé via AskUserQuestion → Raphael a confirmé le pivot de périmètre et salué la correction.

**How to apply:** au démarrage d'un chantier, lister les prémisses factuelles du brief (fichiers nommés, chiffres, états supposés) et les matérialiser avant de planifier : `ls`/parse/`git log` sur les fichiers cités, ET chercher les fichiers VOISINS que le brief n'a pas nommés (settings.json ⨯ settings.local.json, .md ⨯ references/). Si le réel diverge du brief sur un point qui change ce que je touche → AskUserQuestion de périmètre, pas exécution littérale.

**Cas particulier — artefact supposé exister** : un brief peut affirmer l'existence d'un artefact entier (« il y a un script qui réécrivait les docs sur NeoIA », « regarde le module X »). C'est une prémisse comme une autre — chercher exhaustivement (Glob + Grep sur tout le repo, pas un seul dossier ; `git log --diff-filter=D` si « réécriv**ait** » au passé = peut-être supprimé), puis si introuvable, **surfacer comme question, jamais conclure « n'existe pas » en silence** (l'user l'affirme = il a un souvenir, souvent un artefact voisin confondu). Incident 5 juin 2026 : brief « look neo_ia sur le script qui réécrivait les doc sur neoia ». Recherche : client Confluence read-only confirmé (4 GET, zéro POST/PUT vers `/wiki/`), `processor.py`/`ingestor.py` = sens lecture→embed, agent `reformulation` = faux positif (produit NeoChat), neoteem-brain = mêmes scripts de sync. Verdict surfacé comme hypothèse (« tu te souviens probablement des scripts de sync, pas d'un script de rédaction ? »), pas comme conclusion. ⚠️ Piège évité (advisor) : ne pas greper POST/PUT dans un seul sous-dossier puis conclure — étendre à tout le repo.

**Cas particulier — chiffre baseline (consolidé ici)** : tout chiffre baseline annoncé dans un brief (« baseline tests 319 », « fichier 500 lignes », « 30 agents ») est une hypothèse, jamais un fait. Mesurer (`wc -l`, `pytest --collect-only`, `ls | wc -l`) AVANT de raisonner/propager. Incident 28 mai 2026 : brief annonçait « baseline 319 → 324 », mesure réelle = 176 → 181 (écart 143, suite confondue). 2e occurrence : chiffre « 181 tests » porté de session en session dans SELF_PORTRAIT.md, vrai total = 324 (143 mcp + 181 hooks), corrigé avant commit OVERVIEW destiné Boris Cherny. **Règle** : chiffre baseline cité dans SELF_PORTRAIT/CLAUDE.md/RECAP = remesurer à chaque cycle git majeur, jamais relayer sur foi du document. Toujours surfacer « le brief dit X, je mesure Y ».

**Cas particulier — la prémisse vient de MA propre mémoire projet, pas d'un brief humain** : un `memory/project_*.md` (ou un RECAP/RESTE de session passée) est lui aussi une prémisse faillible — il encode l'état du repo à la session N, pas à la session N+1. Le traiter exactement comme un brief externe : matérialiser avant d'exécuter. Incident 26 juin 2026 : `project_spec_unification_3repos.md` disait « RESTE : normaliser les 23 tickets Jira existants à l'ancien format divergent ». Vérif empirique (getJiraIssue ADF sur les 3 Modules + échantillon Stories/sous-tâches) : les tickets avaient été **recréés par le `/spec` unifié les 25-26 juin** → déjà majoritairement conformes (ADF headings colorés #00b8d9, BRIEFs en PJ, étiquettes OK), et il y en avait **29 pas 23**. Le chantier n'était pas « normaliser 23 tickets » mais « corriger une poignée d'écarts précis » (Stories sans section 🧪 dont le Gherkin existe déjà dans le BRIEF = copie ; + cosmétique). Exécuter la mémoire littéralement = re-spec inutile de tickets déjà bons. ⚠️ Piège du diff minimal : ne JAMAIS re-toucher un ticket déjà conforme. Pendant l'audit, fermer les trous AVANT de compter un écart (le BRIEF contient-il le Gherkin à copier ? la sous-tâche est-elle un stub by-design ?) sinon on surcompte comme la prémisse elle-même surcomptait.
